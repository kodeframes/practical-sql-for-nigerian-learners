## Hands-on Lab: test constraints rather than admiring DDL

Create a small practice table separate from MarketLedger:

```sql
CREATE TABLE constraint_lab (
    item_id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku text NOT NULL UNIQUE,
    quantity integer NOT NULL CHECK (quantity >= 0),
    unit_price numeric(12,2) NOT NULL CHECK (unit_price >= 0)
);
```

Insert one valid row. Then deliberately attempt three invalid operations: a duplicate `sku`, a negative quantity, and a `NULL` SKU. PostgreSQL should reject each statement for a different reason.

The exercise is not complete until you can explain which rule rejected which row. A constraint error is evidence that the table is enforcing a declared invariant.

### Lab verification

Inspect the final table contents and confirm the rejected rows did not appear. Then write one additional business rule that this table **cannot** safely express with a simple row-level `CHECK`, especially if the rule depends on data in another table. Choose an appropriate mechanism instead of forcing every rule into one constraint type.
