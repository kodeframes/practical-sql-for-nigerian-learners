# Chapter 18: Transactions, Consistency, and Concurrency Fundamentals — Practice Tasks

### Level A — Apply

Run an update inside `BEGIN`, inspect it, and `ROLLBACK`.

### Level B — Reason

Explain why two statements that represent one business event should often share a transaction.

### Level C — Professional Challenge

Describe a concurrency risk in a stock-reservation workflow where two users try to reserve the last unit at nearly the same time. Propose two broad design strategies without diving into lock syntax.

## Hands-on Lab: observe transaction visibility with two sessions

Open two `psql` sessions connected to the same practice database. In session A, begin a transaction and update a disposable row without committing. In session B, query that row.

At PostgreSQL's usual `READ COMMITTED` isolation level, session B should not see session A's uncommitted change. After session A commits, a new statement in session B can see the committed value.

Do this experiment only on a disposable practice table, not on important data. Then repeat using `ROLLBACK` in session A and confirm session B never observes the rolled-back value as committed state.

### Lab verification

Record the sequence of statements and observations in a two-column table: Session A and Session B. The goal is not to memorise isolation terminology. It is to see that concurrency changes what “current value” means and that transaction boundaries are part of application correctness.
