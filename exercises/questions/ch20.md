## Hands-on Lab: compare plans without inventing performance claims

Choose a query that filters `orders` by branch and date, matching the index supplied in the canonical schema:

```sql
EXPLAIN
SELECT order_id, order_number, order_date
FROM orders
WHERE branch_id = 1
  AND order_date >= DATE '2026-01-01'
  AND order_date < DATE '2026-04-01';
```

Read the plan as evidence, not as a score. On a tiny teaching dataset PostgreSQL may reasonably prefer a sequential scan even though an index exists, because scanning a few rows can be cheaper than using the index. That does not make the index “broken.”

Run `EXPLAIN ANALYZE` only on this safe `SELECT` and compare estimated rows with actual rows. Do not convert the result into a universal claim such as “the index makes the query 10× faster.”

### Lab verification

Document the dataset size, predicate, plan shape, estimates, and actual rows. Performance conclusions without workload context are not reproducible engineering evidence.
