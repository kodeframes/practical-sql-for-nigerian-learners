## Hands-on Lab: turn a vague request into a data question

Suppose a branch manager says, “Show me our best customers.” Do not start with SQL. First, write at least three defensible interpretations: highest completed-order value, highest number of completed orders, or most recent purchasing activity. Each interpretation requires different facts and may produce a different ranking.

Use the MarketLedger data dictionary to identify the tables that would eventually be needed. Customer identity lives in `customers`; order state and date live in `orders`; transaction-time selling values live in `order_items`. Notice that the phrase “best customers” is not stored anywhere. It must be defined.

Write a short analysis note with these headings:

```text
Question:
Metric definition:
Required tables:
Expected output grain:
Important exclusions:
How I will verify it:
```

A strong answer might define the grain as one stored customer account, exclude cancelled orders, and state that anonymous walk-in orders cannot be attributed to a customer because `orders.customer_id` is allowed to be `NULL`.

### Lab verification

Ask another person to read only your metric definition. Could that person write a query that answers the same question you intended? If not, the definition is still too vague. This exercise is deliberately syntax-free. Professional SQL begins by controlling meaning before controlling clauses.
